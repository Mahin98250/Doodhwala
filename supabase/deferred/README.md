# Deferred seller-billing work — not automatic migrations

These are **disposable-test drafts**, not a production rollout. They are intentionally outside `supabase/migrations/`: customer-checkout migrations must not silently depend on the unmerged, conflicting [PR #71](https://github.com/Mahin98250/Doodhwala/pull/71). Applying a draft to a disposable database does not authorize staging writes, create a real payment, or launch an ad.

- `20261028110000_provider_invoice_plan_conflict.sql` proposes a follow-up to PR #71's invoice RPC: a retry for the same provider/month and same plan recovers the original invoice; a different plan is rejected. It does not implement upgrade, downgrade, refund or proration rules. The caller must display the **stored** invoice details, not assume retry inputs replaced them. Its exact-source fingerprint detects drift; it is not authorization or a security mechanism.
- `20261028120000_prepare_inactive_seller_plans.sql` is **for disposable fixture testing only**. An authorized synthetic admin can prepare inactive ₹2,000 normal and ₹3,500 total premium plans. It fails rather than overwrite a conflicting or active plan. Its marker is an operator reminder, not proof of a safe database. It serializes only with itself; PR #71's UI does not share the lock and names are not unique, so never run concurrently with other plan edits.
- `20261028130000_billing_pilot_sponsorship.sql` proposes a private, default-off rollout switch, a conservative dashboard billing reader, and an admin-approved sponsored-placement table/read RPC tied to an **already manually reconciled** premium invoice and its current India-time calendar month. It exposes only eligible, requested seller IDs and expiry to discovery; the seller must also be active, approved, and have a service area. The customer-facing copy remains “Recommended by Doodhwala · Sponsored”. This is a draft technical boundary, not owner approval of calendar billing, campaign duration, tax, reversal or other terms. A payment reference, invoice request, browser choice or UPI-app return is not proof of settlement or an advertising entitlement. The seller cannot enable a placement. The UI flags are rollout switches, **not authorization boundaries for the old PR #71 admin RPCs**; those functions still need independent real-role and security review. An admin can revoke a placement even if the switch is off. The public read fails closed on ineligible status, missing or future-dated payment, seller approval, price/name drift, expiry or rollout failure. The browser clears the tag on offline/hidden state and at its returned expiry, and rechecks while visible; browser scheduling and connectivity mean revocation is not guaranteed to appear instantaneously.

The branch contains [a public pricing preview](../../seller-plans.html), seller/admin screens adapted to the existing PR #71 API, and customer-card rendering. With the default-off/missing server switch, the billing controls do not load invoices or open payment links, and no sponsored tag is shown. The SQL is **not applied** to staging or production. PR #71, the checkout migration, deployed schema/history, function owners and real grants must be reconciled before any rollout. An approved process is still required for receipt disputes, reversals/refunds, audit retention, limits, legal terms and time-zone boundaries. UI checks and source fingerprints are not substitutes for those reviews.

## Reproducing the synthetic integration check

Use only a **new, independently verified disposable PostgreSQL database**, never production or a shared Supabase project. The database name and confirmation setting are reminders, not proof of isolation. The test creates schemas, roles, fake accounts, orders, invoices, a manually recorded fake payment and a synthetic placement, and temporarily switches the draft flags on *inside that disposable database*.

The six unmodified PR #71 sources at `18fc96802e001d5b4d98b84ffe400cca2a5fbc70` are pinned under [`scripts/sql-tests/vendor/pr71`](../../scripts/sql-tests/vendor/pr71/); they are fixtures, **not migrations**. The runner verifies their SHA-256 hashes before touching the database and refuses an existing fixture schema. To use another independently fetched copy, set `PR71_DIR` to that directory.

After setting `PGHOST`, `PGPORT`, `PGUSER`, and `PGDATABASE` to a new disposable database whose name begins `doodhwala_disposable_`, run:

```sh
DOODHWALA_DISPOSABLE_DB_CONFIRMED=yes bash scripts/sql-tests/test-pr71-plan-integration.sh
```

The local PostgreSQL 16.14 run passed with synthetic identities and a stub admin helper. The new test has not been added to the published GitHub Actions workflow: proposed CI changes remain local because the connected GitHub App lacks workflow write permission. A future CI run must be observed on the exact branch SHA before claiming it passed. These checks do not validate deployed Supabase policies, actual admin identity, real bank reconciliation, staged deployment or physical devices. See the [pilot plan](../../docs/MANUAL_CONFIRMATION_PILOT.md) for release gates.
